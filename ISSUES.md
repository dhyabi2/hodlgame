## A. Performance — verified by direct code read (pre-audit, high confidence)

These were confirmed by reading the actual source during scoping; the perf audit

### [ ] PERF-1 (high) — Sequential per-account block fetch
- **Where:** `nano/indexer/multiIndexer.ts:395` (`collectChains`)
- **Why slow:** `for (const account of accounts) ... await this.source.listBlocks(account)` fetches every watched account's chain **one at a time**. With N accounts that is N serial RPC round-trips (each itself several sub-calls). This is the single biggest latency source — it sits under every page.
- **Fix:** `Promise.all(accounts.map(a => this.decodeChain(...await listBlocks(a))))`, or a bounded-concurrency map (e.g. 8–12 in flight) to respect RPC limits. Collapses N serial round-trips to ~1 round-trip of wall-time.
- **Accuracy:** identical result set; order is re-established by `canonicalOrder` after collection, so parallel fetch changes nothing about the folded state. No cache.

### [ ] PERF-2 (high) — `compute()` collects all events twice
- **Where:** `nano/web/server/market.ts:94` then `:110`
- **Why slow:** first `collectEvents(watched)` (line 94), then after the discovery pass `collectEvents([...watched, ...extra])` (line 110) **re-collects everything**, including the accounts already fetched at line 94 — a full second pass over the whole world.
- **Fix:** collect only the newly-discovered `extra` accounts and merge, or run the discovery pass first and collect once. Re-uses the frontier-keyed incremental fetch so unchanged accounts are cheap, but avoids re-decoding the full set.
- **Accuracy:** same union of accounts → same events → same state. No cache.

### [ ] PERF-3 (high) — Sequential `counterparties()` in the discovery pass
- **Where:** `nano/web/server/market.ts:103–108` (nested `for` over pool set × counterparties, `await` each)
- **Why slow:** each pool's `src.counterparties(...)` is awaited serially inside a nested loop — another serial RPC fan-out.
- **Fix:** `Promise.all` the counterparties lookups across all pools.
- **Accuracy:** read-only discovery; parallelizing does not change which accounts are found. No cache.

### [ ] PERF-4 (medium) — `commentsFor` awaited per-token in the feed loop
- **Where:** `nano/web/server/market.ts:227` reached via `toView` inside `feed()`'s per-token loop (`:236`)
- **Why slow:** for a feed of N tokens, N serial durable-store reads for comments — and the feed list view later throws the comments away (`app/api/state` / `feed()` trims them).
- **Fix:** the feed already discards `comments` for the list view — **don't fetch them at all** in `feed()` (pass a flag to `toView` to skip `commentsFor`); fetch comments only in `detail()`. If ever needed in feed, `Promise.all` them.
- **Accuracy:** feed already returns `comments: []`; skipping the fetch changes nothing visible. No cache.

### [ ] PERF-5 (medium) — Client polls three endpoints, each a full-world replay
- **Where:** `nano/web/app/page.tsx` — `/api/state` every 4s (~330), `/api/token` every 3s (~352), `/api/leaderboards` every 8s (~990), plus `receiveAll` 8s and xno-balance 8s
- **Why slow:** on the home view the `state` and `leaderboards` polls run **concurrently**, triggering two independent full-world `compute()` replays every few seconds; leaderboards even calls `feed("")` → a second full `compute()`. Serverless has no shared memory, so nothing is amortized.
- **Fix:** (a) derive leaderboards from the same `feed()` payload the client already fetches (compute once client-side or in one route), instead of a separate endpoint; (b) consolidate onto the existing SSE stream `/api/stream` so the server computes once and pushes, instead of 2–3 overlapping polls. No server cache — just stop asking for the same full replay two ways at once.
- **Accuracy:** one live replay feeding both surfaces is strictly *more* consistent than two replays that can disagree. No cache.
